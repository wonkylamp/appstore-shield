# Guidelines map: rule → check → what a complete fix looks like

Sources: App Review Guidelines (last updated Oct 16, 2026), https://developer.apple.com/app-store/review/guidelines/, and the Apple Developer Program License Agreement (updated Oct 29, 2026). Section numbers follow Apple's current text. Where a check covers several sections, it appears under each.

A "complete fix" removes or discloses a behavior. It never renames, moves or hides it. If a fix only changes what a reviewer would see, it is not a fix.

| Rule | What it says (paraphrased) | Check id | A complete fix |
|---|---|---|---|
| **2.5.19** | No hidden, dormant or undocumented features. Hiding features through obfuscation is grounds for removal and termination. | `review_gating`, `remote_config`, `ota_updates` | Remove every code path that behaves differently in review (sandbox/TestFlight/environment checks, date, region or IP gates, reviewer-account branches) when it changes content, generators, personas or price. Remove dormant features entirely: code, assets, strings and flags. Disclose every remaining remote control and OTA mechanism in review notes. Never obfuscate. |
| **DPLA 3.2(e)** | No code that would "deceive regarding the identity, purpose, or behavior" of the app, "including through post-review modifications that would cause harm to others". | `review_gating`, `remote_config`, `ota_updates` | Same as 2.5.19, plus: after approval, do not change content or price behavior by server switch or OTA. If a change is needed, resubmit or disclose it. Preflight drift output shows what changed since the last approval. |
| **2.1(a)** | Final builds, working demo account, live backend. A built-in demo mode needs Apple's prior approval. | `review_gating`; preflight manual checklist | No reviewer-only demo mode without approval. Provide a non-expiring demo account and working backend; give 2FA steps in notes. |
| **2.3.1(a)** | Describe new features and changes in Notes for Review with specificity. Generic notes get rejected. | `shield_lint_text` (`review_notes`) | Notes that name each change at capability level, which screens and input paths it affects, and what was removed. See review-notes.md. |
| **2.3.1(b)** | Egregious or repeated behavior leads to removal from the Program. | ledger trigger checklist | One complete resubmission per rejection; no churn. |
| **2.3.7** | Name ≤30 characters. No keyword stuffing, trademarks, other app names or prices in name, subtitle, screenshots or previews. | `metadata` | Rewrite the field to describe the app itself. Remove third-party brand and app names and prices. |
| **2.3.8 / 2.3.14** | Icons, screenshots and previews suitable for all ages. Creative assets relevant, with no misleading references, unverifiable claims or discount pricing. | `metadata` | Replace the asset; remove "#1", "best", "uncensored", "no filter" and discount claims. |
| **2.5.2** | No downloading or executing code that adds or changes functionality. | `ota_updates` | Remove remote code evaluation (`eval`, `new Function`, `evaluateScript` on fetched code, dynamic `dlopen`). OTA JS updates may fix bugs but must not add or change features; disclose OTA in notes. |
| **1.1 (1.1.1–1.1.7)** | Objectionable content. 1.1.6 (false information and trick or joke features) says an "entertainment purposes" label does not overcome that guideline; for nudification and NCII, rely on 1.2 and the Oct 16 post, and remove rather than disclaim [inferred]. | `genai_safety` | Remove the capability that produces the content on every input path (picker, free text, remix, upload, deep link, server prompt), and moderate generator output as well as input. No disclaimer substitutes for removal. |
| **1.2** (UGC, including AI content creation) | Four safeguards: (1) filter for objectionable material, (2) a way to report content, with timely responses, (3) blocking abusive users, (4) published contact info. The developer must remove violating content. Failing to remediate identified violations after notice may breach the Code of Conduct; Apple wants removal plus a compliance plan. | `ugc_safeguards`, `genai_safety` | All four safeguards working in the shipped build and reachable from the content itself. Report submissions go to a monitored queue with a stated response time. Remove violating content when notified, and keep a written compliance plan (what was removed, how it is detected, who responds, how fast). |
| **1.2 + Oct 16, 2026 post** (nudification, NCII) | The post names nudification as a bait-and-switch example under 2.5.19, and AI-generated nonconsensual intimate imagery under 1.2. | `genai_safety` (`block`, not suppressible) | Remove undress, clothes-removal, "x-ray" and nude transforms of user photos; remove real-person likeness and face-swap into sexual content; turn provider safety settings back on; replace uncensored models. "Remove", never "add a disclaimer". |
| **1.2.1(a)** | Identify content above the app's age rating and restrict it by verified or declared age. | `ugc_safeguards` (`medium`) | An age signal (declared or verified) and gating for above-rating content; matching age rating questionnaire answers. |
| **4.7, 4.7.1, 4.7.3, 4.7.5** | Chatbots, mini apps and plug-ins: the developer is responsible for content; UGC-style filter, report and block; per-instance consent before sharing data; age gating. | `ugc_safeguards`, `ai_data_disclosure` | Same as 1.2 and 5.1.2(i), applied to chatbot and plug-in surfaces. |
| **5.1.2(i)** | Clearly disclose where personal data is shared with third parties, including third-party AI; explicit permission required. | `ai_data_disclosure` | A consent screen before first use that names the AI provider and the data sent (photos, text, voice). The privacy policy says the same. Review notes name the AI services used. |
| **3.1.1** | Unlocking content needs IAP; restore is required. | `paywall` | Restore Purchases reachable from the paywall and settings. |
| **3.1.2 + DPLA Schedule 2 §3.8(b)** | Subscriptions give ongoing value; describe what the user gets before purchase; no bait-and-switch. Schedule 2 §3.8(b) requires subscription title, length, price (and price per unit where appropriate), and in-app links to the Privacy Policy and Terms of Use. | `paywall`, `remote_config` (price-gating) | Price and period from product data (`displayPrice`), not hardcoded. Trial and renewal terms on the paywall. Terms and Privacy links. Close button visible from the start. No "% off" figures not backed by product data. Price or offer controlled by a remote switch: disclose it, or remove the switch. |
| **4.1(c)** | No other developer's icon, brand or name without permission. | `metadata` | Remove the third-party name or brand from name, subtitle, keywords, icon and screenshots, unless you have written permission (mention it in notes). |
| **4.3** | (a) no multiple Bundle IDs for the same app; (b) no undifferentiated apps in saturated categories; repeated submissions may lead to removal. | ledger trigger checklist | Consolidate duplicates. Do not mass-produce near-identical apps. 4.3 does **not** cover multiple developer accounts; that is the DPLA's Associated Developer Account language. |
| **5.1.1** | Privacy policy in App Store Connect and in the app; consent; data minimization. | `privacy_manifest` | Privacy manifest present; required-reason APIs declared with valid reason codes; `NSPrivacyTracking` matches the SDKs used. |
| **5.1.1(v)** | Apps that let users create accounts must let them delete them in the app. | `account_deletion` | An in-app delete-account flow reachable from settings that deletes the account (not only signs out), including Sign in with Apple token revocation where applicable. |
| **5.6, 5.6.1, 5.6.3, 5.6.4** | Code of Conduct. Respectful review responses; only the system review prompt; no manipulating charts, search, reviews or referrals; excessive complaints and refunds count. A terminated account may submit a written improvement plan. | `ratings_integrity` | Use `SKStoreReviewController` / `requestReview` / `expo-store-review` only. Remove rate-to-unlock rewards, sentiment pre-gates ("Enjoying the app?" before the system prompt) and hardcoded social proof. |
| **DPLA 3.2(f)** | No interfering with the App Store or Program. No misleading, fraudulent or dishonest practices, including bait-and-switch pricing, consumer misrepresentation and deceptive business practices. | all checks + ledger | No single fix exists: a complete record of honest, specific, disclosed fixes; fewer, complete submissions; linted texts. |
| **DPLA 11.2** | Dishonest acts, such as hiding functionality from review or fake reviews, mean immediate termination. Other breaches get a 30-day cure period. | `review_gating`, `ratings_integrity` | Remove the hiding mechanism. Never add one. |

## Evidence tiers for a fix

`RESIDUE_FOUND < UNVERIFIABLE < STATIC_CLEAN < BUILD_CLEAN < PROBED(n/m)`

- **`RESIDUE_FOUND`**: terms, symbols, assets, strings, flags or prompt fragments from the spec are still reachable.
- **`UNVERIFIABLE`**: something cannot be checked from the repo, such as an obfuscated blob or a prompt fetched at runtime.
- **`STATIC_CLEAN`**: the repo sweep found nothing reachable.
- **`BUILD_CLEAN`**: the local built product sweep also found nothing.
- **`PROBED(n/m)`**: n of m probes were blocked by the dev backend. This applies only to the prompts tried.

Only `PROBED` with every probe blocked, plus `BUILD_CLEAN`, supports strong wording in notes, and even then the notes say what was tested.
